# The engines: MatDock, Matcad, Matddns, MatIdentity, MatSMTP

Mattiverse is a layer **on top of** five programs. They are not catalog apps that happen to be installed; they are
the engines, and each of them **owns** one part of the configuration, so it is visible and editable in its own UI:

| Engine | Owns | Mattiverse uses it for |
|---|---|---|
| **MatDock** | stacks (compose + env), containers, backups, schedules, updates | install / update / start / stop / remove an app, its logs, its backups |
| **Matcad** | routes, certificates, DNS providers for certificates, logins | `app.example.com` for every app, wildcard certificates |
| **Matddns** | sources of the IP, DNS records, rules | the DNS record `app.example.com` that follows the home IP |
| **MatIdentity** | people, groups, the apps (OIDC clients) and who may open them | one sign-in for every app and for Mattiverse itself |
| **MatSMTP** | relay users, the accounts mail leaves through, rules, the queue | one relay user per app that sends mail, so all mail leaves through one place |

Mattiverse itself keeps only what no engine knows: users and sessions, shared links, the catalog, the wizard's choices, which
catalog entry an app came from, and where it sits on the home screen.

This page is the **contract**: what every engine offers to Mattiverse. All five speak the same small REST dialect. They are installed in the order of
`EngineIds.All`: MatDock (it deploys the others), Matcad, Matddns, MatIdentity, MatSMTP (registered in MatIdentity as it is deployed); all five are `core: true`.

## Common rules

- Base path **`/api/v1`**, JSON (camelCase), `Content-Type: application/json`.
- **Authentication:** the header **`X-Api-Key`**, compared in constant time with the key from the configuration. **No key
  configured = the API answers `503`** (`{"error":"..."}`), so it can never be reached unauthenticated. A wrong or missing key is `401`.
  The API ignores the session cookie.
- **Errors** are `{"error": "readable message"}` with `400` (invalid input), `404`, `409` (conflict) or `5xx`.
- **`GET /api/v1/status`** answers `{"ok": true, "app": "matdock|matcad|matddns|matidentity|matsmtp", "version": "<informational version>", "apiVersion": 1}`
  (plus whatever the engine already returned). Mattiverse uses `apiVersion` to know what it may call; it must not call an endpoint that a lower
  `apiVersion` does not have.
- **Idempotent writes:** `PUT` and the `POST` upserts can be repeated with the same body without a side effect.
- **`managedBy`:** every object that Mattiverse creates carries `"managedBy": "mattiverse"` (a free string, stored, returned in lists). The engine's own UI
  shows a small **"Managed by Mattiverse"** badge on such objects with the hint that Mattiverse writes them and that manual changes may be
  overwritten. This is how a user who opens the engine sees where a setting came from.
- **Long operations** (MatDock only) are asynchronous: the request answers `202 {"operationId": "..."}` and the output is polled from
  `GET /api/v1/operations/{id}?offset=<chars already read>` →
  `{"id","kind","status":"running|succeeded|failed","output":"<new text>","offset":<next offset>,"finished":bool,"error":null|"text","result":{...}}`.
  Output that is produced only at the end is acceptable; streaming while it runs is better.
- The engine's key is generated by Mattiverse when it installs the engine and handed over as an environment variable (named below).

## Matcad (`ghcr.io/real-ttx/matcad`)

Matcad already had the API (`/api/v1`: `status`, `provider-types`, `providers`, `authentications`, `routes`, `routes/manual`,
`certificates`, `settings`, key `Matcad__ApiKey`). Mattiverse needed these additions (all built, branch `mattiverse-integration`):

1. **`MATCAD_ADMIN_PASSWORD`** (environment): when no user exists, `admin` is created with this password, **without** the forced change, and
   the setup wizard is treated as completed. A value shorter than 8 characters or equal to `admin` is ignored with a warning (Matcad then seeds `admin`/`admin` with the forced change). Without the variable nothing changes.
2. **`PUT /api/v1/settings`** also accepts `"setupCompleted": true` (and returns it).
3. **`GET /healthz`** anonymous, plain `ok`.
4. **`/api/v1/status`** additionally returns `app`, `version`, `apiVersion`.
5. **`managedBy`** on routes, providers and authentications: accepted on `POST`, returned on `GET`, shown as the badge in the lists. A missing
   `managedBy` on an update keeps the stored value, `""` clears it.

Used: `GET/PUT /settings` (`baseDomain`, `setupCompleted`), `POST /routes` (upsert by `id`; **Mattiverse looks the id up by host first**, because a
`POST` without `id` always creates a new route), `DELETE /routes/{id}`, `POST /providers` (`{id?, name, type, credentials, managedBy}`).

**Certificates through the DNS challenge.** Matcad uses a DNS provider only for a **wildcard route**: one `*.domain` certificate, and the
single hosts below it (`app.domain`) are served from it; the `providerId` of a single host is ignored. So with a DNS account Mattiverse creates

```json
POST /routes  {"host": "*.apps.example.com", "wildcard": true, "providerId": 1, "target": "redirect",
               "fallbackUrl": "https://mattiverse.apps.example.com", "enabled": true, "name": "Mattiverse wildcard", "managedBy": "mattiverse"}
```

(other names on the wildcard lead to Mattiverse) and one single-host route per app with `target: "proxy"`. Without a DNS account only the single
hosts exist and Caddy uses the HTTP challenge (ports 80 and 443 must reach the host).

**Routes of the engines themselves.** Matcad's own UI (role `proxy`) is not published through itself; MatDock and Matddns are.

## Matddns (`ghcr.io/real-ttx/matddns`)

Matddns has no management API today (only the push endpoints `/api/update`, `/nic/update`, the monitoring `/api/health`, `/api/state`, and the
anonymous `/healthz`). New: the key is **`MATDDNS_API_KEY`** (environment, config `Matddns:ApiKey`) and the API manages exactly what the UI manages.
Ids are the existing 32-character hex ids. Validation is the same as in the UI. Every write is saved atomically and takes effect without a restart.

| Method and path | |
|---|---|
| `GET /api/v1/status` | as in the common rules, plus `counts: {sources, domains, rules}` |
| `GET /api/v1/sources`, `POST /api/v1/sources`, `DELETE /api/v1/sources/{id}` | `POST` is an **upsert** by `id`, else by `name` (case-insensitive). Body = the source as the UI saves it (`name`, `kind` = `PublicIp`/`Static`/`Dns`/`Push`/..., `intervalSeconds`, the kind's settings object, `entries`), plus `managedBy`. A new `PublicIp` source gets its entry like in the UI. Response = the stored source including all ids. |
| `GET /api/v1/domains`, `POST /api/v1/domains`, `DELETE /api/v1/domains/{id}` | A *domain group* is a provider account with its records: `name`, `kind` (`Cloudflare`/`Netcup`/`Hetzner`/`GoDaddy`/`DynDns`/...), the kind's settings object (credentials), `entries: [{id?, hostname, type: "A"|"AAAA"|"CNAME", recordName?, domain?}]`, `managedBy`. Upsert by `id`, else by `name`. **`entries` is the complete list** of the group (entries that are not in the body are removed, ids that are in it are kept), so Mattiverse can add and remove one host by sending the new list. Credentials are never returned (a `"credentialsSet": true` flag instead). |
| `GET /api/v1/rules`, `POST /api/v1/rules`, `DELETE /api/v1/rules/{id}` | Upsert by `id`, else by the pair (`domainGroupId`, `domainEntryId`). Body as in the UI: `enabled`, `onChange`, `intervalSeconds`, `validatePing`, `validateTcp`, `validationPort`, `domainGroupId`, `domainEntryId`, `sourceEntryIdsInOrder`, `managedBy`. |
| `POST /api/v1/run` | evaluates all rules now (like the periodic check); answers `{"ok":true}` |

The UI marks objects with `managedBy` with the badge ("Managed by Mattiverse") on the sources, domains and rules lists.

What was built, and where it differs from the sketch above (branch `mattiverse-integration`):

- **A record that a rule uses cannot be dropped.** `POST /domains` with a shorter `entries` list answers `409` naming the rule, and
  `DELETE /domains/{id}` is `409` while rules use the group. The API never deletes a rule as a side effect: Mattiverse deletes the rules of the
  records that leave first. (The UI still cascades.)
- `kind` is required on create and cannot change later; an interval of 1 to 14 seconds is a `400` (the UI clamps it); a CNAME on a DynDNS group is a `400`.
- Omitting `entries` on a group leaves its records alone, omitting credentials keeps the stored ones; secrets are never returned (`credentialsSet`).
- Without `domain` on a record the zone is guessed as the last two labels, which is wrong for `example.co.uk`: Mattiverse always sends
  `recordName` and `domain`. Credentials of a provider live in its settings object (`cloudflare`, `hetzner`, `netcup`, camelCase fields), `allowDynamic: true` lets
  Matddns create a record that does not exist yet.
- Deleting a source or one of its entries drops it from the failover lists of the rules, as in the UI. The UI's dynamic (pattern) rules are not part of the API.

## MatDock (`ghcr.io/real-ttx/matdock`)

MatDock has no API today. New: the key is **`MatDock__Api__Key`**. The API works on the **local environment** (the Docker engine of the host,
through the mounted socket) unless `?environment=<name or id>` says otherwise.

| Method and path | |
|---|---|
| `GET /api/v1/status` | common rules plus `environments: [{id, name, type, status}]` |
| `PUT /api/v1/environments/local` | **ensure** an environment of type *Local* exists (name `local`); answers `{id, name}`. Also done at start when `MatDock__Environments__EnsureLocal=true`. `409` if no Docker socket is available. |
| `GET /api/v1/stacks?managedBy=` | every stack of the environment (managed and discovered): `{name, environmentId, managed, managedBy, state: "running"\|"stopped"\|"partial"\|"unhealthy"\|"missing", containers: [{id, name, service, image, state, status, ports}], updatedAt}` |
| `GET /api/v1/stacks/{name}` | the same plus `composeYaml` and `envContent` |
| `PUT /api/v1/stacks/{name}` | **upsert** a managed stack. Body `{composeYaml, envContent, managedBy, deploy: bool, pull: bool}`. Name rule as MatDock's own (`^[a-z0-9][a-z0-9_-]{0,62}$`). `deploy:false` = save only (`200 {stack}`); `deploy:true` = save and `docker compose up -d` (with `pull` first if asked), `202 {stack, operationId}`. |
| `POST /api/v1/stacks/{name}/actions/{action}` | `action` = `start` \| `stop` \| `restart` \| `pull` \| `redeploy` \| `update`. `update` = pull, re-create only if an image changed, body `{backupFirst: bool}` (a bundle backup first, abort if it fails); the operation's `result` is `{"changed": bool}`. `202 {operationId}` |
| `DELETE /api/v1/stacks/{name}?volumes=false` | `docker compose down` (with `--volumes` if asked), then the stack is removed from MatDock. `202 {operationId}` |
| `GET /api/v1/stacks/{name}/logs?service=&tail=300` | `{"text": "..."}` |
| `GET /api/v1/operations/{id}?offset=` | the operation, see the common rules |

Backups (a stack bundle: all volumes + compose + env + image references; MatDock's existing bundle backup):

| Method and path | |
|---|---|
| `POST /api/v1/stacks/{name}/backups` | body `{stopContainers: bool, note: string?, targetId: number?}` (target = the local target by default). `202 {operationId}`, the `result` holds `{"backupId": ...}` |
| `GET /api/v1/backups?stack=` | `[{id, stack, createdAt, sizeBytes, volumeCount, consistent, kind: "manual"\|"scheduled"\|"preUpdate", note, status: "succeeded"\|"failed"\|"running", targetId}]`, newest first |
| `POST /api/v1/backups/{id}/restore` | body `{backupCurrentFirst: bool}`, recreates the stack if it no longer exists. `202 {operationId}` |
| `DELETE /api/v1/backups/{id}` | `204` |
| `GET /api/v1/backups/{id}/download` | the bundle as a `.tar` stream |
| `GET /api/v1/backup-schedules`, `PUT /api/v1/backup-schedules/{name}`, `DELETE /api/v1/backup-schedules/{name}` | a **bundle** schedule: `{stack: string\|null, managedBy, frequency: "daily"\|"weekly", time: "03:00", weekday: "Sunday", retention: 7, stopContainers: true, enabled: true}`. `stack: null` = every stack whose `managedBy` equals the schedule's. Retention keeps the newest *scheduled* bundles per stack. Shows up in MatDock's Schedules page with the badge. |

The compose text that Mattiverse sends carries the block `x-matdock` (name, description, category) that MatDock's launchpad already understands, so the
stack appears there as an app tile.

What was built, and where it differs from the sketch above (branch `mattiverse-integration`):

- **Schedule times are UTC** (MatDock's schedules run in UTC); Mattiverse says so on the schedule form. `stack: null` backs up every stack whose `managedBy`
  matches the schedule's, or every managed stack when the schedule has none. `retention` keeps the newest *scheduled* bundles per stack of that schedule and drops
  failed attempts that a newer success replaced; `0` is unlimited.
- `DELETE` works on stacks MatDock manages only (`404` otherwise); on a stack it does not manage only `start`, `stop` and `restart` are allowed (`409` for the rest).
  `pull: true` without `deploy: true` is a `400`. `state` can be `"unknown"` when Docker does not answer (the list endpoint answers `502`).
- Stacks and `GET /backups` are limited to the chosen environment (`?environment=<id|name>`, default the local one); `GET /backup-schedules` lists all schedules.
- A restore **re-creates a stack that was deleted** (compose, `.env`, volumes), which is how an uninstalled app comes back; Mattiverse then takes the stack
  back as an app (`AppReconciler`) and publishes its route and record again.
- The download is a `.tar` holding the manifest and one tar per volume. Extra fields (`created`, `enabled`, `lastStatus`, `cron`, `nextRunAt`, `safetyBackupId`, ...) are returned and ignored;
  `frequency` reads back as `custom` when the cron was edited in MatDock's UI.
- The `kind` of a backup (`manual`, `scheduled`, `preUpdate`) is chosen by MatDock; Mattiverse's own pre-update and pre-restore backups carry a note and show as manual.

## MatIdentity (`ghcr.io/real-ttx/matidentity`)

The single sign-on of the family (MatDesign docs/PLATFORM.md, "Sign-in with MatIdentity"). Key: `MAT_API_KEY` (the key of its platform `/api`, also the key of its `/api/v1`).
`PUT /api/v1/clients/{clientId}` (`displayName`, `homeUrl`, `redirectUris`, `postLogoutRedirectUris`, `allowSignIn`, `allowMachine`, `callsAllApps`, `managedBy`, `renewSecret`,
`backchannelLogoutUri`) → `clientSecret` only for a new client or a renewed one; `DELETE /api/v1/clients/{clientId}?managedBy=mattiverse`. Mattiverse sets `MATIDENTITY_ISSUER` (its public address) and registers
every app with `identity: {}` and itself (`IdentityLink`, docs/ARCHITECTURE.md "MatIdentity, the single sign-on").
`backchannelLogoutUri` is where MatIdentity posts its logout tokens (OpenID Connect Back-Channel Logout 1.0: form field `logout_token`, a JWT of type `logout+jwt` with
`iss`, `aud`, `iat`, `exp`, `jti`, `events`, `sub` and, unless the person was signed out everywhere, `sid`; five seconds, one more try). Mattiverse always sends it: the app's
address on the shared network (`http://<container>:<port>/signout-backchannel`), Mattiverse's own (`http://<its container>:<its port>/signout-backchannel`), or `""` (removes
it) when there is none; a missing field would leave what MatIdentity has.

## MatSMTP (`ghcr.io/real-ttx/matsmtp`)

The mail relay of the family (MatDesign docs/PLATFORM.md, "Mail through MatSMTP"). Image tags `latest` and `release` from `main`, `nightly` from `dev`. In the container: web **2525**,
SMTP **2025** (STARTTLS), submission **2587**. The catalog publishes only the submission port (`SUBMISSION_PORT`, default 2587) for devices in the network; the apps hand in their
mail on the shared network and **relay users may authenticate on the SMTP port from the Docker network without TLS**.

Environment: **`MATSMTP_API_KEY`** (the key of `/api/v1`; generated, hidden), `MATSMTP_ADMIN_PASSWORD` (at least 8 characters; seeds the administrator, so no first-run page is needed),
`MAT_API_KEY` and the `MATIDENTITY_*` variables (it is a platform app with `identity: {}`). Volume `matsmtp-data:/data`.

| Call | Body / answer |
|---|---|
| `GET /api/v1/status` | `{"app":"matsmtp","version":"…","apiVersion":1,"smtpPort":2025,"smtpTls":"starttls"}` (`none`, `starttls` or `tls`): where the apps hand in their mail |
| `PUT /api/v1/relay-users/{id}` | `{"displayName","allowedSenders":["matbu@example.com"],"managedBy":"mattiverse","renewSecret":bool}` → `{"id","username","password","created":bool}`; `password` only when the user was created or `renewSecret` was set |
| `GET /api/v1/relay-users` | the relay users (`managedBy` with each) |
| `DELETE /api/v1/relay-users/{id}?managedBy=mattiverse` | `204`; `404` when it does not exist; `409` when it is not managed by Mattiverse (it stays) |
| `GET`/`PUT /api/v1/settings` | `{"setupCompleted":bool,"defaultSenderDomain":"example.com"}` |

What Mattiverse does (`MatSmtpClient`, `MatSmtpProvisioner`, `MailLink`):

- **After the install** (`provision: matsmtp`): waits for the API, sets `setupCompleted: true` and `defaultSenderDomain` = the domain of the wizard (when there is one; otherwise
  MatSMTP keeps its own), then connects every app with `mail: {}` and deploys it again. The account MatSMTP delivers through is set in MatSMTP's own UI.
- **Every install and update of an app with `mail: {}`:** `PUT /relay-users/<slug>` (display name = the app, allowed sender = its sender) and the app's `MATSMTP_*` variables:
  `HOST` = MatSMTP's container on the shared network, `PORT` and `TLS` from the status, `USERNAME` from the answer, `FROM` = `<slug>@<defaultSenderDomain>` (else the domain of the
  wizard, else `localhost`), `PASSWORD` kept; `renewSecret` only when the app has no password. MatSMTP installed but not answering: the variables stay as they are. Not installed:
  they are emptied and the app sends its mail itself.
- **Uninstalling an app** deletes its relay user. **MatSMTP comes or goes:** every app with `mail: {}` is connected again and redeployed. **Connect again** (Settings, Engines) and a
  new domain in the wizard set the domain of the senders again and redeploy the apps.

## What Mattiverse does with them

- **Installing an app:** renders the catalog entry to one compose file and a `.env`, then `PUT /stacks/mattiverse-<app>` (MatDock),
  `POST /routes` (Matcad) and, with a domain, the DNS record (Matddns). Uninstalling removes all three.
- **Without the engine API** (an older released image, or the engine is not installed yet) Mattiverse falls back to its own compose
  runner for the stack, so nothing stops working; the settings page says which engines are connected.
- **The wizard** installs the five engines first (MatDock through Mattiverse's own compose runner, because nothing can deploy MatDock before
  it exists; Matcad, Matddns, MatIdentity and MatSMTP then as MatDock stacks), hands each the API key it generated, and asks once for the domain and the DNS provider, which
  goes to Matcad (certificates) and Matddns (records).
